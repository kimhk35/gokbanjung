## 2. 적용 순서와 멈출 지점

1. **백업 확인** — Neon 콘솔에서 현재 시점 복원(Branch/Restore) 가능 여부와 보존 기간을 확인합니다. 확인이 안 되면 **여기서 멈춥니다.**
2. **적용 전 기록** — 읽기 전용 확인:
   `select count(*) from ggc.weeks;` (52 예상) · `select count(*) from ggc.actors;` · `select count(*) from ggc.account_requests;` · `select to_regclass('public.ggc_auth_user'), to_regclass('ggc.stored_files');`
3. **DB 업데이트** — `npm run db:update`(DB 주소 숨김 입력 → `UPDATE` 입력) 또는 Neon SQL Editor에 `DB업데이트_SQL편집기용.sql` 전체를 붙여 실행합니다. 모두 한 트랜잭션이라 실패하면 아무것도 바뀌지 않습니다. 결과가 `완료: …`/`Verified: …`가 아니면 **멈춥니다.**
4. **적용 후 비교** — 2번 숫자가 그대로인지, 두 표가 생겼는지 확인합니다. 다르면 **멈추고** 원인을 확인합니다(새 표는 지우지 않습니다).
5. **코드 배포** — DB 업데이트가 끝난 뒤 PR을 main에 병합해 Vercel 운영 배포를 만듭니다. 순서를 바꾸면 배포 직후 로그인 표가 없어 `setup_required` 안내가 나옵니다(데이터 손상은 없음).
6. **관리자 로그인 되찾기** — 운영 DB에는 Supabase 시절 관리자가 남아 있으므로 최초 관리자 도구는 거부됩니다. 계정 주인을 확인한 뒤 `npm run account:reconnect`로 그 관리자에 새 아이디·임시 비밀번호를 연결하고, 로그인 후 즉시 비밀번호를 바꾸게 합니다.
7. **나머지 기존 계정** — 교사·회원도 본인 확인 후 같은 도구로 재연결합니다. 같은 아이디를 입력했다는 것만으로 연결하지 않습니다. 다시 가입하라고 안내하지 않습니다(새 사람으로 따로 생깁니다).
8. **운영 확인** — 운영 DB에는 시험 가입·시험 게시를 하지 않습니다. 관리자 로그인, 기존 질문 보기, 포스터 다시 올리기처럼 실제로 필요한 작업으로만 확인합니다.

## 3. 소요 시간과 권한

- DB 업데이트: 수 초(표 추가만, 기존 행을 바꾸지 않음). 실행 계정은 Neon 프로젝트 소유자.
- 재연결: 계정당 1~2분. 운영자 PC에서 DB 주소를 숨김 입력.
- 앱은 `DATABASE_URL` 한 개만 사용하고 인증 표는 브라우저용 DB 역할(anon/authenticated)에 열려 있지 않습니다.

## 4. 되돌리기와 한계

- 새 표와 사용자 기록을 지우는 방식으로 되돌리지 않습니다.
- 코드 문제면 이전 배포로 Vercel에서 되돌립니다. 새 표가 남아 있어도 이전 코드는 그 표를 쓰지 않으므로 해가 없습니다.
- 이전 코드는 삭제된 Supabase를 필요로 하므로 되돌려도 로그인·업로드는 다시 동작하지 않습니다(현재 장애 상태로 돌아감).
- 재연결로 바뀐 `ggc.account_requests.user_id`는 이전 Supabase ID로 되돌려도 쓸 곳이 없습니다.
- **복구할 수 없는 것:** 삭제된 Supabase의 옛 비밀번호와 포스터·자료 파일 원본. 포스터는 화면에 "포스터 이미지를 불러올 수 없습니다"로 표시되며, 질문·일정 자체는 남아 있으므로 원본을 다시 올리면 됩니다.
